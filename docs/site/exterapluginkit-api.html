Плагины для exteraiOS

Документация плагинного API клиента tg-ipa. Плагины пишутся на JavaScript и исполняются на JavaScriptCore; имена и форма вызовов повторяют SDK exteraGram для Android, поэтому готовые плагины портируются с минимальными правками.

Что нового в этой версии API

  • Приоритеты хуков — третий аргумент add_hook и add_on_send_message_hook доходит до хоста и задаёт порядок в цепочке.
  • Свизлинг в полной форме Xposed — наборы HookFilter для before/after, MethodReplacement, снятие хука через unhook_method.
  • Опции отправки — scheduleDate (отложенные), спойлер на медиа, замена медиа при edit_message; честные отказы для ttl.
  • themeColors — чтение цветов темы: читаемые имена слотов и Android-ключи key_chat_*.
  • Структурированный логгер — this.logger с уровнями, dump, timed, child, обработчиками записей.
  • Подмножество MVEL в условиях — contains, isdef/undef в строках-условиях пунктов меню и HookFilter.Condition.
  • Мост — приоритеты в сигнатурах addHook/addOnSendMessageHook, новый removeSwizzle.

Как это устроено

Рантайм — JavaScriptCore, а не Python 3.11 с Chaquopy, как в SDK для Android. Форма вызовов сохранена: то же имя метода, те же поля, тот же ответ. Отличается механика underneath, и там, где у iOS нет эквивалента, вызов не делает вид, что сработал, — он записывает в лог отказ с причиной. Например, get_private_field по имени Swift-свойства без @objc вернёт null и объяснит почему. Это сквозной принцип всего API: реальное — работает, невозможное — отказывается вслух.

Значение __sdk_version__ плагина сравнивается с версией поверхности API этого рантайма — сейчас это 1.4.5.0. Базовая версия приложения — 13.1.1; свой минимум плагин объявляет через __app_version__.

Как читать документацию

  • Разделы слева сгруппированы по смыслу: от «Начала работы» к «Портированию с Android».
  • Пометка новое стоит у возможностей, добавленных последним обновлением рантайма.
  • Плашки «Граница платформы» (лавандовая метка) — что отказывается и почему, а не «может сломаться».
  • У каждого блока кода есть кнопка копирования; поиск по всей документации открывается по Ctrl K (или /).
  • Готовые примеры лежат в репозитории в submodules/ExteraPluginKit/js/ — это рабочие плагины, против которых прогоняются тесты.

Формат плагина Plugin file

Один UTF-8 текстовый файл до 4 МБ, открываемый из чата и устанавливаемый там же.

Файл обязан содержать две вещи:

  1. Метаданные — обычные константы верхнего уровня. Загрузчик читает их из текста до вычисления, поэтому это должны быть литеральные присваивания, а не вычисленные значения.
  2. Один класс, расширяющий BasePlugin, под именем Plugin (либо переданный в __extera.register).
var __id__ = "hello_world";
var __name__ = "Hello World";
var __description__ = "Мой первый плагин";
var __author__ = "@yourUsername";
var __version__ = "1.0.0";

class HelloWorldPlugin extends BasePlugin {
    on_plugin_load() {
        this.log("loaded");
    }
}

var Plugin = HelloWorldPlugin;

Рантайм создаёт экземпляр Plugin сам, после вычисления файла, и затем вызывает on_plugin_load. Если плагин строит свой экземпляр иначе, он обязан передать его через __extera.register(instance).

Граница платформы

Файл, тело которого написано на Python (import, def, класс в питон-синтаксисе), отклоняется с сообщением об этом, а не загружается наполовину.

Контейнеры Elyx

Принимается и архив .elyx — формат, который собирает билдер SDK для многофайловых проектов. Это ZIP с YAML-блоком metainfo, деревом assets и одним или несколькими модулями на JavaScript. Точка входа — модуль main из metainfo (или main.elyx.js); модули, которые он запрашивает через require, разрешаются внутри архива с CommonJS-кэшем и защитой от циклов.

# metainfo
id: my_plugin
name: My Plugin
version: 1.0.0
main: src/index.js

Внутри Elyx-плагина глобаль elyx открывает части самого архива: elyx.assets (коллекция ассетов с content / content_bytes / content_string / content_json), elyx.strings (каталоги локализаций с pluralize), elyx.metainfo, elyx.refmap, elyx.settings, elyx.get_environment(), elyx.import_module(name) и elyx.Asset.from_path. elyx.temp_asset_from_url здесь асинхронный (в SDK для Android он синхронный): принимает колбэк и вызывает его с готовым ассетом.

Граница платформы

Питон-части стека Elyx — import_module в семантике Python, wheel-колёса с Python ABI, mvel_execute, Java-прокси gen/gen2 — не имеют iOS-эквивалента: это стабы, которые бросают исключение с причиной, а не исчезают молча.

Жизненный цикл Lifecycle

Три метода; включение и выключение плагина вызывают их предсказуемо.

class P extends BasePlugin {
    on_plugin_load() {      // включение; и на старте приложения с включённым плагином
    }
    on_plugin_unload() {    // выключение; и при остановке приложения
    }
    on_app_event(event) {   // значение AppEvent
    }
}

Значения AppEvent: START, STOP, PAUSE, RESUME (строки 'start', 'stop', 'pause', 'resume'). START доставляется после загрузки, так что к этому моменту on_plugin_load уже отработал.

Правило

Всё, что плагин запустил вне клиента — таймер, наблюдатель, долгий запрос — должно быть остановлено в on_plugin_unload.

Хуки Hooks

Хуки регистрируются внутри on_plugin_load. Метод, который существует, но не был зарегистрирован, никогда не вызывается — та же ловушка, что и в SDK.

on_plugin_load() {
    this.add_hook("messages.setTyping");      // TL-имя через точку
    this.add_hook("TL_account_updateStatus"); // написание TL_ тоже матчится
    this.add_hook("messages.", true);         // match_substring: целое пространство имён
    this.add_hook("account.updateStatus", false, 10); // приоритет 10
    this.add_on_send_message_hook(7);         // исходящие сообщения, приоритет 7
}

Приоритеты хуков новое

priority — третий аргумент exteraGram: чем больше число, тем раньше метод выполняется в цепочке. Равные приоритеты не описаны в SDK, поэтому этот рантайм сохраняет порядок загрузки — тот же порядок, который используют все остальные цепочки здесь.

Методы-хуки

МетодСигнатураМожет менять
pre_request_hook(name, account, request)request
post_request_hook(name, account, response, error)ничего (наблюдательный)
on_update_hook(name, account, update)ничего (наблюдательный)
on_updates_hook(name, account, updates)ничего (наблюдательный)
on_send_message_hook(account, params)params

name — оба написания в одном: колбэк получает форму TL_ (TL_messages_setTyping, TL_updateNewMessage), а регистрация в любом из написаний матчит другое.

params хука отправки — это {message, peer, account}. Возврат HookResult.cancel() отбрасывает отправку; замена params.message и возврат HookResult.modify("params", params) переписывает текст.

Отсоединённые хуки

post_request_hook и хуки апдейтов — detached: они выполняются на очереди скрипта после события, и ничего из возвращённого ими не доходит до клиента. Медленный плагин не может затормозить через них состояние аккаунта — и не может переписать апдейт.

pre_request_hook вызывается синхронно, на сетевом потоке, через очередь скрипта. Он обязан быть быстрым.

Форма данных

Запросы и апдейты пересекают мост как объекты полей; вложенное TL-значение — объект с _ (имя конструктора) и собственными полями, до глубины 8. Поэтому update.message.peer_id и update.message.id читаются так же, как на Android.

Для хуков по методам самого приложения (случай Xposed) — см. Свизлинг.

Свизлинг Xposed-хуки на методы

Хуки раздела «Хуки» покрывают TL-трафик. Чтобы дотянуться до метода самого приложения — случай Xposed — используйте hook_utils.find_class и .hook, которые подменяют Objective-C-метод в рантайме.

var cls = hook_utils.find_class("SpeakerNode");  // загруженный ObjC-класс, или null
var hook = new MethodHook();                    // колбэки задаются ниже
var token = cls.hook("setMessage:", hook);

На практике плагин задаёт MethodHook двумя колбэками:

var hook = new MethodHook();
hook.beforeHookedMethod = function (param) {
    var args = param.getArgs();      // ресивер и до двух объектных аргументов
    // param.setResult(x) заменяет возврат метода и пропускает оригинал
};
hook.afterHookedMethod = function (param) {
    // наблюдение после оригинала; тоже может setResult
};
hook.setPriority(50);                // порядок хуков на одном методе
hook_utils.find_class("SomeClass").hook("someSelector:", hook);

param несёт собственные методы SDK: getArgs, getArg(index), setResult, getResult, getObjectExtra(key), setObjectExtra(key, value).

Что можно хукать

  • Можно: Objective-C-метод, который уже существует на загруженном приложением классе, принимает ноль, один или два объектных аргумента и возвращает объект или ничего.
  • Нельзя: Swift-метод без @objc (нет селектора, который можно найти), C-функцию, метод со структурой или примитивом в аргументах, и всё, что должно было бы существовать до запуска плагина. Класс или селектор, которые ни во что не разрешаются, попадают в лог; они никогда не создаются.
Отказ с причиной, а не поломка

Сигнатура вне этого набора отклоняется с причиной — hook("foo:") на методе с аргументом CGFloat отвечает null и пишет в лог type encoding. Подсвизлить его блоком, возвращающим объект, не крашнулось бы сразу — но испортило бы возвращаемое значение каждого вызова, и это куда хуже ловить потом. Блок диспетчеризуется с арностью, которая у метода реально есть, так что метод без аргументов не получает два неинициализированных регистра.

Порядок выполнения

Колбэки выполняются в порядке Xposed, оригинал вызывается всегда, если хук не заменил результат:

  1. beforeHookedMethod(param) — выполняется первым. param.setResult(x) пропускает оригинал и становится возвращаемым значением метода. Ничего не вернул — оригинал выполняется.
  2. оригинальная реализация;
  3. afterHookedMethod(param) — выполняется с param.getResult(), равным тому, что вернул оригинал. Чтение ничего не меняет; setResult здесь заменяет результат.

Значения setResult пересекают мост как JSON: массив приходит массивом, null приходит как nil, а не как строки "[]" и "null".

Хуки ставятся один раз на пару класс+селектор (вторая установка — no-op) и все восстанавливаются при выгрузке плагинов, так что блок удалённого плагина не может продолжать работать.

Фильтры before/after новое

cls.hook(selector, hook, kind, options) принимает списки фильтров из SDK: options.before_filters / after_filters берут массив (или один) предикатов HookFilter. Фильтр, ответивший false, пропускает только этот колбэк — оригинальный метод и хук after всё равно выполняются. Здесь реален полный набор HookFilter:

  • RESULT_IS_NULL / NOT_NULL / IS_TRUE / IS_FALSE;
  • ResultEqual / ResultNotEqual;
  • ResultIsInstanceOf — пишет в лог один раз и пропускает (нет Java-класса для проверки);
  • ArgumentIsNull / NotNull / IsFalse / IsTrue;
  • ArgumentEqual / ArgumentNotEqual;
  • ArgumentIsInstanceOf — то же обращение;
  • Condition(expression, object) — с подмножеством MVEL (см. «Поверхности Android»);
  • Or(...).

MethodReplacement новое

MethodReplacement работает: возвращаемое значение replace_hooked_method(param) становится результатом метода, оригинал пропускается; undefined означает «ничего не заменено», и оригинал выполняется.

Снятие хука: unhook_method новое

Токен, который возвращает hook, можно снять посреди сессии:

var token = cls.hook("someSelector:", hook);
// …
this.unhook_method(token);   // true, когда хук был снят

Снятие пары делает следующий hook по ней свежей установкой.

Граница платформы

hook_utils.get_private_field / set_private_field не имеют эквивалента — Swift-свойство без @objc недостижимо по имени — и пишут в лог вместо того, чтобы угадывать.

HookResult и HookStrategy Результаты хуков

Ответ хука сообщает хосту, что сделать с операцией.

HookResult()                                             // ничего не просим
HookResult({strategy: HookStrategy.MODIFY, request: request})
HookResult.cancel()
HookResult.modify("params", params)
СтратегияДействие
HookStrategy.DEFAULTничего особенного
HookStrategy.CANCELостановить операцию (pre-request, отправка)
HookStrategy.MODIFYиспользовать возвращённый объект; его увидят следующие плагины
HookStrategy.MODIFY_FINALизменить и остановить цепочку

Поле, несущее замену, зависит от хука: request, response, update, updates, params. Хуки выполняются в порядке загрузки плагинов на путях отправки и pre-request; первый cancel останавливает цепочку.

Пункты меню Menu items

Свои строки в контекстном меню сообщения, меню чата, ящике и профиле.

on_plugin_load() {
    this._item = this.add_menu_item(MenuItemData({
        menu_type: MenuItemType.MESSAGE_CONTEXT_MENU,
        text: "Инфо о сообщении",
        icon: "msg_info",
        subtext: "Отладка",
        priority: 10,
        on_click: (ctx) => this.log("id=" + ctx.message.id),
    }));
}

on_plugin_unload() {
    if (this._item) { this.remove_menu_item(this._item); }
}

menu_type: MESSAGE_CONTEXT_MENU, DRAWER_MENU, MAIN_MENU, CHAT_ACTION_MENU, PROFILE_ACTION_MENU.

Поля MenuItemData: menu_type, text, on_click, item_id, icon, subtext, condition, priority. add_menu_item возвращает id пункта (устойчивый item_id, если задан, иначе сгенерированный).

Условие condition

condition может быть функцией или строкой-выражением. Строка компилируется один раз на форму контекста и видит каждый ключ контекста как переменную, поэтому dialog_id > 0 читается так же, как версия на MVEL в exteraGram. Условие, которое бросает или не компилируется, скрывает пункт.

Контекст клика

on_click получает объект контекста: account, peer_id, dialog_id и всё остальное, описывающее место, из которого открыто меню. Выведите Object.keys(ctx) в лог, чтобы увидеть, что конкретное меню предлагает.

Существующие пункты снимаются автоматически при выгрузке; remove_menu_item — чтобы сделать это раньше.

Экран настроек ui.settings

Реализуйте create_settings() и верните список контролов.

create_settings() {
    return [
        Header({text: "Общие"}),
        Switch({key: "enabled", text: "Включить фичу", default: true,
                subtext: "Пример переключателя", icon: "msg_settings",
                on_change: (value) => this.log("switch: " + value)}),
        Selector({key: "mode", text: "Режим", default: 1,
                  items: ["Выкл", "Базовый", "Расширенный"]}),
        Input({key: "name", text: "Имя", default: "Alice"}),
        EditText({key: "token", hint: "Токен", multiline: false}),
        Divider({text: "Секция"}),
        Text({text: "Подстраница", icon: "msg_arrow_forward",
              create_sub_fragment: () => this._sub_page()}),
        Text({text: "Внимание", red: true}),
        Custom({text: "Своя строка", on_click: (row) => this.log(row.key)}),
    ];
}

_sub_page() {
    return [Header({text: "Подстраница"}), Text({text: "Вложенные настройки."})];
}

Примечания

  • Контролы — обычные объекты: new Switch({...}) и Switch({...}) работают одинаково.
  • Контрол с key персистится под ним. Без ключа он выводится из text/hint плюс индекс строки — устойчиво между запусками, потому что текст устойчив. Text принимает и явный key — для переводимого текста.
  • Сохранённый переключатель доходит до get_setting и on_change как настоящее булево, не 1: plugin.get_setting("x", false) === true — корректная проверка.
  • on_change(value) получает новое значение. on_click(row) и on_long_click(row) получают {key, getKey()} — Android-View здесь нет, и ключ строки стоит вместо него. Плагин, который только логирует или выполняет свою логику, не замечает разницы.
  • create_sub_fragment(), возвращающий список, открывает вложенную страницу.
  • link_alias на строке Text/Custom без on_click открывает экран, названный алиасом: plugins — единственный разрешающийся алиас (открывает список плагинов). Прочие алиасы пишутся в лог, потому что у iOS нет deeplink'ов по ключам настроек, куда их можно было бы направить. Строка с собственным on_click сохраняет его; link_alias — запасной вариант, как в SDK.

var row = PreviewFactory({"link_alias": "sticker_preview"});

// PreviewFactory.instance.java — написание того же объекта из документации SDK

Очереди и потоки Schedulers

Одна очередь скриптов на все плагины; всё медленное — через run_on_queue.

this.run_on_queue(fn);                     // сериализуется на очереди скриптов
this.run_on_queue(fn, 2500);               // через 2500 мс
this.run_on_queue(fn, GLOBAL_QUEUE, 2500); // имя очереди принимается и игнорируется
this.run_on_ui_thread(fn);                 // работа главной очереди (диалоги, бюллетени)
android_utils.run_on_ui_thread(fn, 500);

Константы очередей существуют для формы и принимаются, затем игнорируются — очередь скриптов одна: STAGE_QUEUE, GLOBAL_QUEUE, CACHE_CLEAR_QUEUE, SEARCH_QUEUE, PHONE_BOOK_QUEUE, THEME_QUEUE, EXTERNAL_NETWORK_QUEUE, PLUGINS_QUEUE.

Правило

Всё медленное — сеть, файловый ввод-вывод, парсинг — идёт через run_on_queue. Очередь скриптов общая для всех плагинов: заблокировав её, вы блокируете все плагины разом.

Отправка сообщений client_utils

Каждый хелпер принимает замыкающий объект опций; account в нём выбирает аккаунт, иначе используется аккаунт хука или выбранный.

this.send_text(peerId, "Привет из плагина");
this.send_text(peerId, "**Привет** из *плагина*!", {parse_mode: "Markdown"});
this.send_text(peerId, "Это ответ.", {replyToMsg: 9876});

this.send_photo(peerId, "/path/image.jpg", {caption: "Вот.", high_quality: true});
this.send_document(peerId, "/path/file.zip", {caption: "Вот архив."});
this.send_video(peerId, "/path/video.mp4", {caption: "Смотрите!"});
this.send_audio(peerId, "/path/song.mp3", {caption: "Слушайте!"});

this.send_message({peer: peerId, message: "Отложенное", scheduleDate: 1735689600, notify: false});
this.send_message({peer: peerId, caption: "<b>Жирно</b>", photo: "/path/p.jpg", parse_mode: "HTML"});
this.send_message({peer: peerId, message: "Шапка", entities: [new TLRPC.TL_messageEntityBold()]});

this.edit_message({peer: peerId, id: messageId}, "Новый текст.");
this.edit_message({peer: peerId, id: messageId}, "Новое фото.", {file_path: "/path/another.jpg"});

parse_mode нечувствителен к регистру и принимает HTML и Markdown. Когда он задан, маркеры форматирования превращаются в entities на JS-стороне тем же парсером, что использует parse_text; без него текст идёт как набран, и клиент сам находит голые ссылки и упоминания. Для медиа parse_mode применяется к caption. high_quality читается из high_quality/sendingHighQuality.

Опции отправки и их семантика новое

  • везде уважаются: account, replyToMsg, notify, caption, parse_mode, entities;
  • scheduleDate (unix-секунды) ставит сообщение в список отложенных — в тот же, куда складывает «отправить позже» сам композер; читаются оба написания (scheduleDate/schedule_date);
  • hasMediaSpoilers / with_spoiler / has_media_spoilers закрывают медиа спойлером при отправке — атрибут едет в атрибутах сообщения, которые прикладывает композер;
  • file_path (+ photo/video/audio для вида) на edit_message заменяет медиа: то же декодирование локального файла, что на пути отправки, так что картинка декодируется в пузырь-картинку; без него редактирование только текстовое;
  • ttl отказывается вслух в логе и игнорируется — per-message TTL в этом движке не существует (TTL — свойство секретных чатов, а не одного сообщения);
  • with_spoiler при редактировании тоже отказывается в логе: у edit-запроса движка нет слота под атрибут, поэтому редактирование не может добавить спойлер.

Модульные формы

Те же функции существуют на уровне модуля:

client_utils.send_text(peerId, "привет", {account: account});
client_utils.get_client(account).send_text(peerId, "привет");
client_utils.parse_text("<b>x</b>", "HTML");
client_utils.get_client_version();   // "13.1.1", или "Unknown"
client_utils.get_hook_account();     // аккаунт сработавшего колбэка, иначе null
client_utils.get_selected_account();

get_client(account) возвращает AccountClient: send_text, send_photo, send_document, send_video, send_audio, send_message, edit_message плюс get_account().

Два имени, которые не глобальны

Два имени, которые SDK кладёт в топ-уровень, здесь достижимы только через объект модуля. Это не «починено» в документации, потому что так устроен сам билд — и плагин, написанный по SDK, на этом наткнётся:

  • parse_text — не глобаль. Используйте client_utils.parse_text(...) или extera_utils.text_formatting.parse_text(...). Строка var p = parse_text(...) из SDK бросит здесь ReferenceError.
  • SimpleSettingFactory — не глобаль. Используйте ui.settings.SimpleSettingFactory(...) (тот же объект, что __extera.api.SimpleSettingFactory).

BasePlugin и контролы настроек — настоящие глобали, так что порт работает на них без правок.

Мультиаккаунт Multi-account

Каждый вошедший аккаунт держит своё соединение и продолжает стрелять хуками. Каждый колбэк получает account — и всё, что он делает, должно его использовать.

on_update_hook(name, account, update) {
    var client = this.client(account);   // следует за скоупом хука
    client.send_text(update.message.peer_id, "ответ");
    return new HookResult();
}
  • this.client(account) / this.client() / get_client(account) — хелперы, привязанные к аккаунту;
  • this.get_hook_account() / get_hook_account() — аккаунт сработавшего колбэка, null вне колбэка;
  • get_selected_account() — аккаунт, видимый в UI, когда нужно именно это;
  • работа, запланированная run_on_queue из колбэка, сохраняет аккаунтовый скоуп этого колбэка.

Форматирование текста Text formatting

HTML и Markdown в entities — одним парсером на JS-стороне.

var parsed = client_utils.parse_text("<b>Жирно</b>, <i>Курсив</i>, <a href='https://example.com'>Ссылка</a>", "HTML");
// {message: "Жирно, Курсив, Ссылка", entities: [{type, offset, length, url?}, ...]}

var cap = client_utils.parse_text("**Жирно**", "Markdown", true);  // is_caption → ключ "caption"
// extera_utils.text_formatting.parse_text — та же функция

TLEntityType: BOLD, ITALIC, UNDERLINE, STRIKETHROUGH, SPOILER, CODE, PRE, TEXT_LINK, BLOCKQUOTE, CUSTOM_EMOJI.

HTML

<b>, <strong>, <i>, <em>, <u>, <ins>, <s>, <del>, <strike>, <code>, <pre language="...">, <spoiler>, <tg-spoiler>, <blockquote>, <a href>, <emoji id>, <br>; пятёрка XML-сущностей и числовые ссылки на символы.

Markdown

**жирно**, *жирно*, _курсив_, __подчёркнуто__, ~~зачёркнуто~~, ~зачёркнуто~, ||спойлер||, `` `код` ``, тройные кавычки с языком, [текст](url), ![alt](tg://emoji?id=123), > цитата, **> цитата.

Смещения entities — в UTF-16, и по ним индексируют обе стороны: и JavaScript, и хост.

Сборка entities вручную

Экспортирован и RawEntity — extera_utils.text_formatting.RawEntity({offset, length, type, url, language, document_id, collapsed}), промежуточная форма, которую SDK превращает в TLRPC; используйте её, когда плагин строит entities руками.

Классы TLRPC.TL_messageEntity* существуют как простые записи (Bold, Italic, Underline, Strike, Strikethrough, Spoiler, Code, Pre, TextUrl, Blockquote, CustomEmoji) — экспорт, собирающий entity руками, сохраняет форму. send_message читает offset/length/type с того, что ему дано, и они имеют приоритет над parse_mode.

Прокси Proxy

Чтение и правка списка прокси клиента; локальный MTProxy, который поднимает сам клиент.

proxy.list(function (r) {
    // r = {ok, servers: [{link, kind, host, port}, ...]}  kind: mtproto|web|socks
});

proxy.add(["tg://proxy?server=1.2.3.4&port=443&secret=dd..."], function (r) {
    // r = {ok, added, skipped}
});

proxy.remove_all(function (r) { /* r = {ok, removed} */ });

proxy.own_peer_id(function (r) { /* r = {ok, peer_id} */ });
proxy.own_peer_id(account, function (r) { });

var parsed = proxy.parse_link("tg://proxy?server=1.2.3.4&port=443&secret=ee...");
// {kind: "mtproto", host, port, secret, subtype: "faketls"|"padding", link}
var key = proxy.protocol_key(parsed);   // "mtproto_faketls" | "web_websocket" | "socks" | ...

add принимает ссылки, не объекты. list отдаёт весь список, а не активный сервер. parse_link — чистый JS, отвечающий null для всего, что не читается. Всё алиасится и как client_utils.proxy_list / client_utils.get_own_peer_id.

Локальный MTProxy

Граница платформы

Плагин не может открыть сокет: iOS не даёт JavaScript-контексту ни сокетов, ни способа слушать порт. Слушателем владеет клиент — это единственная способность, которую плагин не может построить для себя.

proxy.local_start(domain) поднимает MTProxy на 127.0.0.1 (порт 1443, если свободен, иначе эфемерный) со свежим dd-секретом, добавляет запись tg://proxy?server=127.0.0.1&port=…&secret=dd… в список прокси и делает её активной — трафик клиента сразу идёт через неё, а запись видна в Настройки → Конфиденциальность → Прокси точно так же, как добавленная руками.

domain — зона CloudFlare, где отвечают имена kws<dc>.<domain> (схема tg-ws-proxy). Туннель набирает kws<dc>.<domain> по WSS, при неудаче откатывается на kws<dc>.web.telegram.org, затем на адрес датацентра — зона, переставшая отвечать, не роняет транспорт. Необязательный массив domains называет дополнительные зоны для набора по порядку — тот же фолбэк, который получает приложение-референс из своего списка зон.

proxy.local_start("pclead.co.uk", function (r) {
    // r = {ok, status: {running, host, port, domain, active, connections,
    //                   upstreams, link, error, upstream_error}}
});

// Выбранная зона первой, остальные — запасные.
proxy.local_start("pclead.co.uk", ["offshor.co.uk", "cakeisalie.co.uk"], function (r) {});

proxy.local_stop(function (r) { /* r = {ok, status: {...}} */ });

var s = proxy.local_status();   // тот же объект статуса, синхронно
  • start на уже работающем прокси только восстанавливает его запись (домен тогда необязателен);
  • stop снимает запись и возвращается к прямому соединению, только если этой записью была активная — прокси, добавленный пользователем руками, не трогается никогда; stop выполняется при выключении или выгрузке плагина, но не при уходе приложения в фон;
  • local_status синхронный: он читает состояние, которое клиент уже держит, — как раз то, что нужно строке настроек; на сборке без этого моста он отвечает {ok: false, running: false, error};
  • active говорит, что запись — та, которой пользуется Telegram; connections и upstreams — что трафик реально идёт. Они сообщаются, а не угадываются: это и позволяет плагину отличить «подключено» от «запущено и ждёт». upstream_error несёт последнюю ошибку туннеля.

Плагин tg_ws_proxy в js/ — референсный пользователь этого API.

HTTP http

Запросы отвечают через колбэк. Никогда не блокируют.

http.get("https://example.com/list.txt", {headers: {"Accept": "text/plain"}, timeout: 10}, function (r) {
    if (!r.ok) { this.log("не вышло: " + r.error); return; }
    this.log(r.status + " " + r.text);
});

http.get_json("https://example.com/actual.json", function (r) {
    if (r.ok && r.json) { this.log("версия " + r.json.version); }
});

Форма ответа: {ok, status, text, error, json?}. Транспортная ошибка или не-2xx — это ok: false; status и text остаются, когда есть тело: тело 404 часто объясняет неудачу. get_json парсит text и кладёт результат в json; нераспарсиваемое тело — ok: false с сохранённым текстом.

Глаголы помимо GET

Реализованы post, put, patch, delete и общий request; каждый берёт объект опций с headers, body (строка или значение для JSON-сериализации), timeout и тот же колбэк:

http.post("https://example.com/items", {body: {name: "x"}, headers: {"Content-Type": "application/json"}}, cb);
http.put("https://example.com/items/1", {body: JSON.stringify({name: "y"})}, cb);
http.patch(url, {body: "..."}, cb);
http.delete(url, {headers: {...}}, cb);

// Общая форма — для метода, которого нет в списке выше.
http.request("OPTIONS", url, {headers: {...}, body: "..."}, cb);

Варианты *_json (post_json, put_json, patch_json) парсят тело ответа в r.json, как get_json. Тело запроса, не безопасное для UTF-8, переносится через мост как base64; http кодирует и декодирует его на стороне JavaScript, потому что btoa в JavaScriptCore отсутствует.

Всё алиасится и как client_utils.http_get, client_utils.http_post, client_utils.http_put, client_utils.http_patch, client_utils.http_delete, client_utils.http_request и формы *_json.

Файлы file_utils

Пути в каталогах приложения; байты — как base64-текст.

file_utils.get_cache_dir();

Байты — это base64

read_file_bytes / write_file_bytes несут base64-текст, а не байтовый массив: массив байтов не пересекает строковый мост. Учитывайте это в переносимом плагине, вместо того чтобы притворяться, будто bytes(...) работает.

Каждый путь заперт в собственных каталогах приложения через хост, поэтому плагин не может выйти за их пределы.

FilesController сохраняет форму (SUPPORT_ICONS, Place, FileInfo, OnClickArgs, три типа исключений, register/unregister) — ради import-строк и ссылок на enum. SUPPORT_ICONS — false, а register пишет в лог, что перехвата открытия файлов на iOS нет: срабатывает собственная ветка «не поддерживается» плагина, а не хендлер, который молча никогда не стреляет.

Внешний вид Appearance hooks

Плагин отвечает на запросы, которые экран задаёт при своей сборке; клиент применяет ответ своей палитрой и анимацией. Регистрировать нечего — реализуйте метод, и хост его вызовет.

on_allow_screenshots(account, null, extra)true — разрешить скриншоты везде

extra несёт account и, где известен чат, peer. message — тот же объект-полей, что получают хуки апдейтов. Ответы меню вложений и строк настроек могут называть только ключи, которые были предложены, — ключ, которого плагин не видел, игнорируется: плагин не может скрыть то, чего перед ним не было. Цвета — числа 0xRRGGBB; отсутствующий флаг значит «включено»; отсутствующий secondary — «без градиента».

Анимация вставки сообщения

Все поля необязательны, кроме duration:

{
    duration: 400,        // мс
    delay: 0,
    alpha: 0,             // стартовая прозрачность, по умолчанию 1
    scaleX: 0.8, scaleY: 0.8,
    scaleToX: 1, scaleToY: 1,
    translationX: 0, translationY: 0,
    rotationZ: 0, rotationX: 0, rotationY: 0,
    curve: "decelerate",  // linear|decelerate|accelerate|accelerateDecelerate|overshoot|spring
    overshoot: 0,
    rotationKeyframes: [0, 10, -10, 0]
}

extra для on_message_inserted добавочно несёт isDate, width, height. Для вставки, name-цветов, theme-цветов и скрытия сообщений побеждает ответ первого плагина: два плагина не могут одновременно анимировать одну строку или владеть одной палитрой.

Если плагин меняет цвет после отрисовки экрана, он вызывает __extera.notifyAppearanceChanged() (это же делает this.set_setting(..., true)) — палитра пересобирается.

Чтение текущих цветов: themeColors новое

Плагин может прочитать цвета, которыми живёт тема прямо сейчас:

var colors = __extera.themeColors(["outgoing", "inBubble", /* … */]);
// {outgoing: 0x…, inBubble: 0x…}; имени без эквивалента в этой сборке просто нет в ответе

Читаемые имена: исходные слоты accent, accentTextColor, button, header, link, floatingButton, outgoing, navigationBar, actionSheet; добавленные inText, outgoingText, inBubble, chatList, plainBackground, separator, inputPanel; и Android-ключи, за которыми порт тянется в первую очередь — key_chat_outBubble, key_chat_inBubble, key_chat_inText, key_chat_outText, key_chat_listBackground, key_windowBackgroundWhite, key_graySection, key_chat_inputPanelBackground — каждый отобразится на слот с тем же смыслом.

Сохранённые удалённые сообщения Saved deleted messages

Плагин хранит копию сообщения, которое пользователь удаляет, — и строка остаётся в чате после того, как сообщение исчезло из Telegram.

on_messages_will_be_deleted(account, {messages}, extra) срабатывает перед самым удалением клиентом сообщений, которые пользователь удалил с этого устройства. Сервер о них не объявляет никогда (messages.deleteMessages отвечает только affectedMessages), поэтому это единственная точка, где текст ещё существует. Сообщения, удалённые кем-то другим, приходят как обычные апдейты updateDeleteMessages / updateDeleteChannelMessages / updateDeleteScheduledMessages — плагину, которому нужны оба случая, надо зарегистрировать и то, и другое: ровно это делает UPDATE_HOOKS в re_extera_dex.

Храните копии где удобно (JSON-файл под file_utils.get_plugins_dir() переживает пересборку). Затем отвечайте на два запроса:

// Строки, которые клиент должен нарисовать в этом чате.
on_deleted_messages(account, {peer_id}, extra) {
    return [{
        id: 830646,          // id исходного сообщения, Int32, не ноль
        date: 1735689600,    // unix-секунды, не ноль
        text: "текст",
        media_kind: "photo", // необязательно; показывается, когда нет текста; "none"/"" — ничего
        sender_id: 123456,   // необязательно
        is_out: false,
    }];
}

// Пользователь удалил сохранённую строку в клиенте; выкиньте копию.
on_forget_deleted_messages(account, {peer_id, message_ids}, extra) {
    // удалить каждый id из хранилища и пересобрать кэш
}
  • Клиент спрашивает on_deleted_messages один раз на чат и только когда хоть один плагин его реализует. Ответы всех слушающих плагинов склеиваются и дедуплицируются по (peer_id, id).
  • Строка без пригодного id или date отбрасывается — ноль поставил бы её в конец чата.
  • peer_id — это PeerId.toInt64(); канал — channel_id + 2 * 2^32, и сравнение с update.message.peer_id из хука апдейтов работает напрямую.

Нарисованная строка выглядит как настоящее сообщение, но помечена удалённой: чуть прозрачнее, с красной иконкой корзины перед временем. Она выбирается, как любое сообщение, поэтому «выделить → Удалить» убирает её — клиент вызывает on_forget_deleted_messages с её id и пересобирает список. Это единственный способ убрать сохранённую строку: она существует только в хранилище самого плагина.

Логирование Logging

Простой this.log — и структурированный логгер в придачу.

this.log("loaded");                     // наследие, пишется всегда
android_utils.log({some: "object"});   // не-примитивы инспектируются

Структурированный логгер новое

Описанный в SDK логгер здесь настоящий:

this.logger.debug("чат %s: %s", chatId, state);  // %-подстановка; форматируется,
                                               // только когда уровень включён
this.logger.info("готов");
this.logger.warning("странно, но выжило");
this.logger.error("запрос не удался", excInfo); // excInfo.stack едет строкой
this.logger.exception(err);                    // внутри catch: сообщение + стек
this.logger.dump(obj, "user", 3, 20);          // DEBUG-инспекция объекта
var t = this.logger.timed("sync"); ... t.end(); // "заняло N мс"; end(true) добавит "(failed)"
var net = this.logger.child("net");            // тег plugin.<id>.net, наследует порог
this.logger.add_handler(record => { /* … */ });// record: {level, tag, message, traceback, created, text}
this.logger.level = LogLevel.DEBUG;            // или "debug", или 20; null вернёт умолчание
  • Уровень гейтит запись до форматирования сообщения: горячий хук, пишущий на DEBUG, ничего не стоит, пока DEBUG выключен.
  • dump помечает циклы <cycle>, режет глубину через {...}, ограничивает массивы и объекты по max_items с хвостом + N more и никогда не вызывает геттеры.
  • log_utils — настоящий модуль: get_logger("name"), LogLevel и чистая dump(value, label, depth, max_items); порог по умолчанию — INFO, переключателя dev-mode нет: для подробного прогона ставьте logger.level = LogLevel.DEBUG.

Лог — один файл на все плагины (Library/extera-plugins.log), читаемый с экрана плагинов в клиенте. Не-примитив рендерится как JSON, так что this.log(update) — рабочий способ инспекции полезной нагрузки.

Хук молчит? Смотрите лог

Выброс внутри колбэка плагина перехватывается рантаймом и пишется в лог против id плагина; наружу в клиент он не попадает никогда. Из-за этого плагин с брошенным кодом выглядит подписанным и ничего не делает — первым делом проверяйте лог, когда хук кажется мёртвым.

Поверхности Android Android-only surfaces

Эти имена существуют, чтобы import-строки и ссылки на enum разрешались. Где возможен эквивалент — он настоящий; где нет — вызов пишет в лог, а не притворяется.

ПоверхностьПоведение
hook_utils.find_classреально: разрешает загруженный Objective-C-класс и возвращает хэндл с .hook(selector, hook). Неизвестные имена — null.
hook_utils.get_private_field / set_private_field + статические вариантыпишут в лог и отвечают null / false: Swift-свойство без @objc недостижимо по имени.
Xposed-форма MethodHook / HookFilter, find_class(...).hook(...)реально на Objective-C-методах: хост свизлит селектор, выполняет before, вызывает оригинал (если before не заменил результат), затем after с установленным getResult(). Непереносимая сигнатура (структура/примитив) отклоняется с type encoding, а не ставится с неверным ABI.

TLRPC несёт классы message-entity — и ничего сверх того.

Прокси контроллеров Controller proxies

Геттеры client_utils.get_*, которым достаточно данных, которые можно отдать плагину, работают поверх настоящих вызовов хоста и отвечают асинхронно — в той же форме колбэка, что и HTTP-мосты.

Имена — наши

Имена методов наши, не Android'овские: перенесённый плагин получает те же данные через get_messages(peer_id), а не через вызов Java. Так порт доходит до данных без изменений логики.

var messages = client_utils.get_messages_controller();
messages.get_messages(peer_id, 50, function (r) {
    // r = {ok, messages: [{id, peer_id, date, text, out, has_media, action, ...}, ...]}
});

var contacts = client_utils.get_contacts_controller();
contacts.get_peer(peer_id, function (r) { /* r = {ok, peer: {...} | null} */ });

var cfg = client_utils.get_user_config();
cfg.getClientUserId(function (r) { /* r = {ok, peer_id} */ });
cfg.getCurrentAccount();   // разрешённый числовой id аккаунта

var media = client_utils.get_media_data_controller();
media.get_media(peer_id, 50, function (r) { /* r = {ok, media: [...]} */ });

var queue = client_utils.get_queue_by_name("name");
queue.run(fn); queue.run_after(fn, 250);

get_messages_controller().send_message(peer, text, options) пробрасывает в собственный send_text плагина и выполняется без ожидания — как send в SDK. delete_messages пишет в лог, что сообщение удаляется из UI чата, а не через контроллер, и отвечает {ok: false}. get_notifications_settings().get отвечает данными peer-профиля — именно за ними к нему и обращаются.

Peer id на мосту

Peer id — это PeerId.toInt64(): упакованная форма самого клиента, то же число, которое сообщает pluginMessageDetailsJSON и которого ждёт send_message. Это не Telegram-пометка каналов вида -100…: та — конвенция Bot API, клиент внутри себя её не использует; peer id из хука должен годиться для отправки, поэтому обе стороны идут через один кодек и возвращаются в исходном виде. Передавайте peer id, полученный из хука, в любой вызов моста как есть.

Интенты Intents

intents.IntentsManager регистрирует глобальные before/after-хендлеры для URL, которые открывает приложение: tg://, https://t.me, deeplinks — всё, что ОС вручает клиенту. URL парсится, хендлеры матчятся по scheme/host/path/query, сортируются по возрастанию приоритета и вызываются со значениями, названными их собственной сигнатурой.

var IM = intents.IntentsManager;

var handle = IM.new_global_before_handler(function (host, id) {
    this.log("чат " + id);
    return true;                 // не дать URL открыться
}, {scheme: "tg", host: "chat", required_path_args_names: ["id"]});

var after = IM.new_global_after_handler(function (host) {
    this.log("открыт " + host);
}, {scheme: "https", host: "t.me"});

handle.unhandle();               // снять один
IM.unhandle(after.handler_id);   // снять по id

Фильтры

scheme, host, path (лидирующий / добавляется при отсутствии, шаблоны {var} захватывают значения), required_path_args_names (на практике — обязательные имена query-аргументов), priority (меньший выполняется раньше). action, type, categories, whitelist_flags, blacklist_flags принимаются и матчатся по значениям «Intent», выведенным из URL; открытая ссылка — это ACTION_VIEW без типа и категорий, если URL их не намепил.

Before-хендлер, вернувший true, останавливает оставшиеся before-хендлеры и собственную обработку URL клиентом — iOS-форма param.setResult(true). After-хендлер остановить ничего не может; он выполняется, когда URL уже обработан.

Колбэк вызывается только с параметрами, которые он называет: intent, scheme, host, path, query_args, action, flags, type, categories — плюс любой query-аргумент или переменная path-шаблона по имени. Функция без читаемой сигнатуры получает весь объект контекста (случай **kwargs); функция, назвавшая ...args, получает стандартный позиционный набор.

  • IM.parse(url) возвращает {scheme, host, path, query} — та же форма, которую видит хендлер.
  • IM.unhandle(id) бросает HandlerNotRegistered для неизвестного id.
  • IM.send / IM.startActivity на iOS смысла не имеют (этому приложению нечего отправлять другим приложениям) и пишут в лог.

Хост вызывает __extera.dispatchUrlIntent(url) перед открытием и __extera.dispatchUrlIntentAfter(url) после; клиент подключает первый в AppDelegate.handleOpenURL, так что before-хендлер с true действительно предотвращает открытие.

Портирование с Android Porting checklist

Порядок правок, превращающих плагин из SDK для Android в плагин этого рантайма.

  1. Уберите строки from … import … — имена глобальны, кроме parse_text и SimpleSettingFactory, которые живут только под client_utils / ui.settings (см. «Отправка сообщений»). Эти два квалифицируйте вручную.
  2. def → class P extends BasePlugin { … }; self → this.
  3. Именованные аргументы → один замыкающий объект опций: send_text(peer, "x", parse_mode="HTML") → send_text(peer, "x", {parse_mode: "HTML"}).
  4. Метаданные остаются литеральными присваиваниями верхнего уровня.
  5. isinstance, генераторы списков, str.format → JavaScript-эквиваленты.
  6. Зарегистрируйте в on_plugin_load каждый реализуемый хук.
  7. Ставьте защиту на геттеры контроллеров — здесь они отвечают null.
  8. parse_mode в одном месте: JS-парсер — тот же, что у client_utils.parse_text.
  9. Проверяйте через node js/test — bootstrap.test.js гоняет настоящий bootstrap.js против фальшивого хоста с той exact-формой моста, которую реализует Swift-сторона.

Что обычно ломается при портировании

  • Сокеты и потоки. Их нет у JS-контекста на iOS. Сетевой транспорт выносится в хост: см. как устроен локальный MTProxy в разделе «Прокси» — плагин только рулит, слушателем владеет клиент.
  • Java-классы и DEX. InMemoryDexClassLoader, рефлексия по Java-классам, генерация классов из Python — эквивалента нет. Поведение DEX-модулей воспроизводится декомпиляцией и портом логики на JS-хуки: прецедент — re_extera_dex.
  • Activity result / системные файл-пикеры. На iOS нет onActivityResult; бэкапы и выбор файлов делаются через file_utils и свои экраны настроек.
  • Android-View и интенты наружу. Кастомных View нет — строки и экраны настроек; URL-схемы наружу урезаны: IntentsManager.send пишет в лог.

Ориентир по объёму: плагины «чистой логики» поверх Telegram-API (фильтры, автоответчики, форматирование, сторедж) портятся почти механически по чеклисту выше; плагины с локальной сетью переносят транспорт в хост; плагины с DEX-пейлоадами — только поведение, после декомпиляции.
